# ADR-0027: Run operator screens in their own Node-RED instance

- **Status:** Accepted
- **Date:** 2026-11-09
- **Deciders:** Jarek (OFM project, with Claude)
- **Tags:** screens, runtime, security

## Context

Step 3a.8 brings OFM's first operator screen, the line view: machine
states, KPIs, the work order with *Start*, *Changeover done* and
*Complete*, and stops waiting for a reason. Node-RED Dashboard 2.0 is
already in OFM's image (the simulator's panel uses it), so the screen could
simply be another tab of the runtime's flow. But the runtime collects the
data and writes the historian: like a PLC, it should keep running whatever
a screen does. A screen bug, or many browsers at once, would share its
process and its event loop (one thread). The runtime's database role may
also write history directly, which a screen should never need.

## Decision

1. **Own container.** The screens run in a second Node-RED container,
   `ofm-screens`, from OFM's own image, with their own flow file
   `flows/ofm-screens.json` (ADR-0016). The line view is
   `https://<server>:1882/dashboard` (port 1882 through the proxy,
   ADR-0019); the screens' editor is `https://<server>:1882`.
2. **Live values from the UNS.** The screens subscribe, as the read-only
   MQTT user `ofm_reader`, to each line's `…/workorder` and `…/kpi/+` and to
   each machine's `…/state` and fault code. They never publish.
3. **The database through a few functions only.** The screens log in as
   `ofm_screens`, which can read no table. It may call only the functions
   of migration 018: `config.fn_screen_model()` (lines, machines in flow
   order, reasons, products, planned orders), `hist.fn_screen_stops_to_code`
   (stops waiting for a reason), sign-in (ADR-0028), and recording as a
   signed-in person (`config.fn_person_*`, which call the recording
   functions of migrations 015 and 016 with their checks).
4. **Changes reach every screen through the normal path.** An order
   started on a screen is recorded in the database; the runtime publishes
   it on `…/workorder` (ADR-0010), and every screen and the simulator see it
   from there. The screens re-read the model and the stops every 30 s and
   after each action.

## Alternatives considered

1. **A tab in the runtime's flow.** One container less, but screens and data
   collection would share one process and one database role with write
   rights on history. Rejected.
2. **Grafana for the line view.** Good for looking, but buttons that record
   (start an order, code a stop) need a plugin and a write path with
   per-person sign-in. Grafana stays for analysis (*Line OEE*, step 3a.8b).
3. **A separate web application** (its own server and front end). Most
   freedom, but a second technology to maintain; Node-RED with Dashboard 2.0
   is already in the image and known. Rejected for now.

## Consequences

- Positive: a screen can never stall data collection; the screens' rights
  are a short list of functions; the runtime stays headless.
- Negative: one more container (about 100 MB of memory), one more database
  password in `.env` (`OFM_SCREENS_DB_PASSWORD`, generated by
  `make-env.sh`), one more port (1882) to open on the plant network.
- Follow-up: supervisor screens (recoding, food-safety verification,
  ADR-0015) and SPC entry (Phase 3c) are built in the same container.
